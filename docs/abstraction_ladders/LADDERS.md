# Ladder register

One row per candidate Ladder for the Abstraction Ladder Experiments ([ABSTRACTION-LADDERS-2026-07-16.md](ABSTRACTION-LADDERS-2026-07-16.md) — the design doc; all terms per its §2). This is **state, not events**: rows advance status, get corrected, or get rejected — findings and run records never accumulate here (they go to `EXPERIMENTS.md` and the ladder's worksheet).

**Discipline:**

- **One folder per row** — `ladders/<name>/` holds the worksheet (`worksheet.md`, copied from [ladders/TEMPLATE.md](ladders/TEMPLATE.md)) plus the generated artifacts: `spec.md` (structure, from `LadderSpec.render()`), `results.md` + `report.json` (from the ladder report) — all written by `arc-lab run-ladder <name> --artifacts ladders/<name>/`. The worksheet holds design work and narrative; generated artifacts own structure and results; this file only indexes.
- **`alN-<slug>` identity.** A ladder is a durable asset (registry key + testbed + `LadderSpec`), so it gets a stable ID — unlike an `EXPERIMENT_QUEUE.md` row, which is ephemeral and stays nameless. `N` is minted when the ladder is adopted here (row + folder); the slug is the anchor competence (eg `al7-count-markers-per-region`). The number is an **identifier, not a ranking** — gaps from rejected ladders are expected and fine. Still distinct from E-numbers, which are minted per _run_ in `EXPERIMENTS.md`: one ladder may carry many E-numbers.
- **Source-of-truth handoff.** Once a ladder becomes code (`LadderSpec` + generator + testbed), the spec owns the structure — the worksheet keeps rationale + dead ends only. Sized-to-run → one EXPERIMENT_QUEUE.md row pointing at the worksheet. Run → EXPERIMENTS.md entry.
- **Rows persist after running** (a certified ladder + its testbed is a reusable asset). Delete a row only if the ladder is abandoned _and_ its worksheet records why. **A rejected ladder's row stays** — the rejection is the finding.
- **Statuses:** `sketch`
  - `linted` (static checks pass)
  - `tasks-drafted`
  - `certified` (oracle-chain empirical checks pass)
  - `admitted` (in the batch)
  - `run`
  - Terminal: `rejected` (reason in the worksheet; if the reason is itself a finding — eg a no-foothold gap — log it in `EXPERIMENTS.md` too)
- **Status vs Verdict.** `Status` is where the ladder sits in the pipeline; `Verdict` is what its empirical certificate said when it last ran. They differ on purpose for the **controls** (al9–al12), which are designed to fail: a control that is correctly rejected has done its job, so it stays `run`, not `rejected`.

## How to read this table (all 20 ladders ran 2026-07-20)

- **Every row below has been built and run.** Verdicts are the empirical certificate (`tractable_jumps` · `no_skip_paths` · demonstration health), not the static lint. Static lint passes on 18 of 20 (al10 and al12 fail by design).
- **`inconclusive` is not a pass.** Since the 2026-07-20 stop-limit work `no_skip_paths` is tri-state: a _censored_ search is unsolved, and unsolved would otherwise read as "no skip path found". `None` fails admission exactly as `False` does (design doc §6.9).
- ⚠ **Reproducibility caveat.** The al1–al14 runs were made with a `considered_limit=50000` compute guard that is **not carried in the committed `LadderSpec`s**, so `arc-lab run-ladder al3-quad-symmetrize` today recomputes uncapped instead of hitting cache. al15–al20 ran as-committed and are cache-clean. Resolving this is the open "should the reference config carry a `considered_limit`?" decision (EXPERIMENTS.md 2026-07-20 → Next) — it enters `run_id` _and_ becomes part of what the certificate is anchored against.
- **Artifacts are thin.** Only al1, al2 and al5 have committed `results.md` / `report.json`; the other 17 verdicts are read from cached runs and not yet written out. al15–al20 have **no `ladders/<name>/` folder at all** (code + testbed only) — rows link to their registry module until one exists.

## Batch summary (2026-07-20)

- **20 built and run**: 8 admitted with full rung recovery (al1, al2, al15–al20), 7 rejected on structure, 4 controls (2 functioning as designed, 2 compromised by an inherited spine), 1 inconclusive.
- **Two collapse families identified**, both general rather than incidental — **self-similar doubling** (al3/al7/al9/al11: `r_2k == r2^k`, transform-independent) and the **Family-B perceiver collapse** (al5/al6/al8: cheap perception erases the gap the ladder was meant to bridge).
- **The rebuild worked.** al15–al20 were designed against exactly those two findings and all six certify clean — including the first tall non-collapsing tower (al17) and the first goal-layer recombination (al18/al19).
- **Structure is the binding constraint, not learning.** Every rejected ladder except al5/al6/al13 recovered its rungs: the climbs largely worked, the _ladders_ were unsound. That inverts the expected failure mode and is the batch's main methodological lesson so far.
- **Open, in priority order:** (1) al2's extrapolator validation — al1's 78x–530x depends on it; (2) al14's re-run at a guard that lets it finish; (3) the `considered_limit`-in-reference-config decision (the al1–al14 reproducibility gap); (4) the al19/al20 fan-in definition; (5) rebuilding al9/al11 on al17's spine; (6) writing the 2026-07-20 screen into `EXPERIMENTS.md` and giving al15–al20 their folders — these findings currently live only in code docstrings and this register.
